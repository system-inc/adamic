# Test quality measurement: is every test worthy, good, right and true?

You measure the quality of the Go tests of ONE unit of github.com/system-inc/adamic: __UNIT__. Take the scope from `go test -list . ./__PACKAGE__/` at your starting commit, not from a file name: tests move between files while they're being split, so a file can be empty by the time you start. When your unit is a slice of a big package, it is the rows named under "Your rows" at the end of this brief; check each name exists in that list, and say which moved or vanished. Adamic is TypeScript's syntax and types, proven rather than erased, compiled to native code through C and clang, with no garbage collector. Its tests are its gate, so they have to be held to the standard the types are held to: proven, never trusted.

## The four questions, for every row in your unit
A row is a top-level Test function, or a whole family (see Families below). Every count in this brief (mutants per row, unique kills, subsumption) is over rows, after families are grouped.
1. Worthy: what does this row catch that no other row in the package catches? You show it by planting a mutant (a small deliberate break in the code under test) that THIS row fails on. Uniqueness across the repo is settled later by a central replay of your diffs, not by you.
2. Good: what does it cost? Run it alone three times (`-count=1` each) and report the median wall seconds of the test binary's own line (`ok ... 2.9s` or `--- PASS (2.9s)`), plus nproc.
3. Right: what decides its expected answer? Pick one: "external-run" (the test actually runs Node, Go cohere, git, ESLint, Prettier, tsc or test262 and compares), "external-authority" (the expected values are hand-copied from an outside authority such as tsc's diagnostic text or the ECMAScript spec; name it and say whether you checked one value against it), or "self" (a snapshot of our own output, or a hand-written value with no outside authority).
4. True: can it fail? Show a mutant it catches. A test no mutant can make fail is untrue.

## Demonstrate, never opine
Every claim needs evidence you produced in this session: the mutant (file, line, the one-line change), the command, and the failing line. Don't write "looks redundant" or "seems important". If you can't show it, say "cannot judge" and why. That's a good answer.

First, name two things in writing before any mutant: the CODE UNDER TEST (what the test is checking, e.g. Adamic's lowering, or the .a port of a cohere package compiled natively) and the ORACLE (what decides the right answer, e.g. Go cohere, git, Node). Mutate only the code under test. Never mutate the oracle, the harness or the test itself: a mutant in Go cohere's matcher tests the oracle, not Adamic. For stage1 ports the code under test is the port's source (.a or .ts); a port mutant needs a native rebuild. A compiler mutant (internal/lower and friends) changes every native product, so give each mutant its own build cache, `ADAMIC_BUILD_CACHE_DIR=/tmp/<unit>/cache/<mutant>`, or you'll read a stale product. (ADAMIC_NATIVE_SPLIT is not a cache key: it only switches splitting on when it equals 1.) What worked: the port reads a selector from a file (e.g. /tmp/adamic-mutant) that you write before each run, so one switched source builds once per product. Otherwise accept one rebuild per mutant, use at most four mutants, and report each rebuild's time.

How to plant mutants (the mutants come from the code, never from the tests):
- First list the code under test: every function in the package that your unit's rows reach. Then write the mutants from THAT list with a fixed menu, before checking which test fails: flip a condition, change a constant or an option, drop a statement, return early, off-by-one a bound, swap two arguments. Spread them over the code, not one aimed at each test. A mutant written to make one particular test fail proves nothing about uniqueness.
- Empty-answer probes are not mutants: list them in "probe_kills", never in "kills" or "unique_kills", and never rest sacred or subsumed on them.
- The menu is the whole menu. Inserting a statement is not on it; if you plant one anyway, mark it supplemental and rest no verdict on it.
- Aim for about three mutants per row and at most 20 in the unit. Past 20 the matrix eats the budget.
- Add the empty-answer probe, one per distinct entry of the code under test your rows call (Lower, a port's main function; not the preparation helpers before it, such as Load when the code under test is lowering): make it return its empty value at entry (nil, zero, empty list). Judge each row only by the probe on the entry it calls. If a row still passes its own entry's probe, set "vacuous": true: the row can't tell a working answer from no answer. That's a finding, not a verdict. A row whose positive subcases pass the probe while a negative subcase fails it is not vacuous, but list those subcases in "vacuous_subcases". A row you didn't probe gets null, never a guess.
- Put them all behind one switch so you compile once, e.g. `if os.Getenv("ADAMIC_MUTANT") == "M3" { ... }` in a scratch copy, then run with different values. Revert after.
- The kill matrix is the run: each mutant against the whole package, `timeout 120 go test -json -count=1 -timeout 90s ./__PACKAGE__/ -run . > MN.log 2>&1`, recording exactly which rows fail. The outer `timeout 120` is only a backstop for compiling; the budget is the test binary's 90 s. You don't need a separate first-catch run: the matrix's failing line is the evidence.
- A run still going at 90 s is cooked: report it as over budget, and don't wait.
- A panic aborts the whole test binary, so rows after it never ran. Rerun each of your rows alone for that mutant and record only what you observed; the rest stay unknown.
- Every standalone diff must apply to origin/main and compile with the tool that builds it (`go vet ./<mutated package>/` for Go, the runtime's clang flags for C, the port's own build for .a and .ts). Dropping a statement can leave an unused variable: drop the whole loop or statement instead, and say so.
- A kill is package-unique if exactly one row fails on it (a family whose members fail counts once).
- Big packages (internal/oracle, internal/lower, internal/native run for many minutes): time the whole package once at the start. If it's over 90 s, don't run it per mutant. Find the tests that reach the mutated function (a coverage profile, or git grep for the function's callers in _test.go files) and run the matrix over those, listing them. Say that kills outside that set are unknown.
- Survivors matter: a mutant no test catches is unguarded behavior. Report every survivor with a one-line witness that behavior really changed (e.g. the function's output before and after). That's a finding, not a failure on your part. A survivor whose output you can't make differ is an equivalent candidate: report it as one, never as unguarded.
- Narrow the same way when a mutant's whole-package run cooks, even if the clean baseline fit: rerun that mutant over the rows that reach its function, and mark the row's result bounded.
- Big-package slices: your matrix can't see the whole package, so it can't prove package uniqueness. Don't call a row cannot-judge for that. Give it the verdict your bounded matrix supports, set "bounded": true, and list the rows you ran in the matrix. The central replay runs every diff over every reached package and settles uniqueness after you.
- Repo-wide uniqueness isn't your job: don't run other packages (that run goes over budget). Instead, save every mutant as a standalone unified diff against origin/main (one file per mutant, no switch), so the whole suite can replay it later and settle repo-wide uniqueness centrally. Put the diffs in your final message, or push them on test-audit/__SLUG__ and give the path.
- Give every file:line against the origin/main commit you started from, not your scratch copy.

## Families and witnesses (judge these differently)
- A family: tests that run one checker over different inputs, all one test cut into pieces. Generated or hand-written makes no difference: the test is the family when its members differ only in the input they hand the same function (TestProduct_TsgoArchive, TestProduct_LengthArchive and their siblings that each call one shared check with a different recipe are one family). The usual shapes: numbered shards plus their union (TestX_000..._NNN, TestXUnion), units (TestXUnit01...), corpus units named for a fixture (TestX_<path>_<12 hex>) together with that corpus's coverage and remainder tests, and per-input wrappers sharing a name prefix and a checker. Give it one row, named for the prefix with "family" after it, and list its members. A family is never subsumed by its own member. When you can't tell whether two tests share a checker, read both bodies; if a member asserts something its siblings don't, it's its own row.
- A witness: a test whose job is to prove that ANOTHER check can fail, e.g. a planted-failure test, a test that applies its own built-in mutants and expects the agreement check to catch them, or a test named ...Mutant(s) or ...PlantedFailure. Production mutants don't apply to it, because it passes whether the port is right or wrong. Judge it by weakening the check it witnesses: this is the one harness edit you're allowed, in a scratch copy. Disable or loosen that comparison and show the witness now fails. Verdict "witness" if it does, "untrue" if it still passes.

## Verdict per test
- sacred: it is the only row in the package that catches at least one mutant written from the code (not aimed at it), and its oracle is named.
- slow-worthy: worthy, but over 60 s on its own.
- untrue: no mutant you planted made it fail, after an honest try at the code it claims to cover.
- subsumed: every mutant it catches is also caught by one other named row in the package. Name it in "subsumed_by" and give its median in "subsumer_seconds", whichever is faster: which of the two to keep is the defender wave's call, not yours. Two rows that subsume each other are both subsumed, each naming the other. With a small mutant set this is a hint, not a deletion: say how many mutants it rests on.
- overlapping: every mutant it catches is caught by some other row, but no single row catches them all (list them in "subsumed_by"). Keep it; it's a defender's question, not a deletion.
- setup-check: a row whose code under test is the suite's own construction (shard assignment stability, corpus coverage, a family's setup). Production mutants can't reach it; judge it like a witness, by breaking the construction it checks in a scratch copy, and give "setup-check" if it fails, "untrue" if it doesn't.
- helper: a Test function that is only a subprocess entry (it returns at once unless an environment variable its parent sets is present). It has no verdict of its own; name the parent row that runs it.
- witness: a witness that fails when the check it guards is disabled (see above). Its failures under production mutants don't count: a broken precondition isn't proof the check works. Only the weakened-check run decides it.
- cannot-judge: you couldn't build a meaningful mutant (say why).

## Rules
- Start: `git fetch origin && git checkout -b test-audit/__SLUG__ origin/main`. Read CLAUDE.md first, then your unit's test files whole, then the code they test.
- Toolchain: if /workspace/adamic-tools/env.sh already works in your workspace, skip setup. Otherwise `bash cloud/setup.sh`, then source the env.sh it prints. Report its timing and nproc. Warm tools don't mean warm Node dependencies: before your baseline, run `npm ci` in stage3/api (and in any directory your package's tests load node_modules from). Then run the package once clean; a red baseline means stop and report, never audit on red. Rows that skip by default behind an opt-in (an ADAMIC_ORACLE_* variable, a missing SDK or corpus): enable them when the tool is installable in your workspace, and list every row that still skipped. A big package whose whole run times out isn't red: narrow it as below.
- Watch the oracle's strength, not only whether it fires. A row that checks only an exit code, or a count, can pass for the wrong reason (a different failure with the same code). When a survivor or a catch looks like that, say so in the row's "oracle".
- Never push to main and never open a pull request. You may push your scratch branch test-audit/__SLUG__ with the mutant switch as evidence, or skip pushing.
- Test output goes to a log file, never piped.
- No em-dashes in what you write.

## Final message (this is the deliverable)
Start with a five-line summary. Then a JSON array, one object per top-level test (one per family):
{"test","package","file","seconds","oracle","oracle_kind" (one of the three, or a list when the row checks two things, e.g. Node runs it and a self-written NotYet label must match),"kills":[mutant ids],"unique_kills":[mutant ids],"last_proven_fail":"<mutant id and failing line, this session>","verdict","subsumed_by","mutants_in_matrix","probe_kills":[probe ids],"subsumer_seconds":<median of the subsumer, when subsumed>,"vacuous":<true if its own entry's empty-answer probe passed it>,"bounded":<true for a big-package slice>,"matrix_rows":[the rows your matrix ran, when bounded],"evidence":"<command and failing output line>"}
Then the mutant table: id, file:line on origin/main, the change, which rows failed (empty means survivor). Then the survivors, one line each, each with its witness or marked equivalent candidate. Then every place this brief was unclear, wrong or cost you time: that is half the deliverable. Then how long setup, building and running took, and what you didn't cover.

## Budget
About 20 minutes for the unit, 30 for a stage1 port (its cold lowering and native builds run a minute or more). If a step goes past 90 s, it's cooked: stop it, narrow it, and say what you narrowed.
