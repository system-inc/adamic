# 42849: excess JavaScript type arguments can be absent

Observed: compiler/conformance runner 0 present, 0 absent. Final API fixtures
6 present, 8 absent. This function is exposed through the checker API;
ordinary compilation does not query every argument's contextual constraint.

Each absence is in excess.js.txt, querying argument positions 1 and 2
(zero-based) of C<string, number, boolean> against a one-parameter C. There
are two syntactic parents: a JSDoc TypeReference in @type, and an
ExpressionWithTypeArguments in @extends. Each is run with noImplicitAny false
and true: 2 positions x 2 parents x 2 settings = 8 absences. The index and
arity are recorded for every absence in fixture-observation.json. Node catches
TypeError: Cannot read properties of undefined (reading 'resolvedBaseConstraint').

The six present reads are the valid I<string> control in excess.ts.txt and
the first C argument in each JavaScript parent, at both settings. The excess
I alias is an error type before this read. The final TypeScript fixture also
queries call, new, tagged template, decorator, expression-statement
instantiation, variable-initializer instantiation, type alias, class extends,
and interface extends positions. Call-like parents take the separately guarded
signature helper. TypeScript excess reference/heritage arguments return an
error type before this read. The expression-statement instantiation takes its
own signature path. The final fixture output retains all returned constraints
and diagnostics rather than inferring absence from diagnostic counts.

Code explanation: getTypeFromClassOrInterfaceReference returns errorType on
invalid arity in TypeScript. For JavaScript it deliberately continues past
that error. Consequently getTypeParametersForTypeReferenceOrImport can return
a genuine one-element parameter list for an excess-argument JavaScript node.
The surrounding condition does not establish a bound on typeArgumentPosition.

Disposition: no assertion and no adapter edit. proposed-42849.diff.txt is an
explicit absent-case throw preserving the observed caught TypeError name and
message. proposal.cjs evaluates it only in memory in Node's existing build.
All 14 final fixture program observations equal the unmodified build's results,
including all 10 errors across both proposed rows. Nothing was built from this
proposal. Error stack frames move; full uncaught stderr identity is not claimed.
Correctness must rule on this JavaScript change before it ships.
