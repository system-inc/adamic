# Method values read through views

TypeScript v6.0.3, 050880ce59e30b356b686bd3144efe24f875ebc8. Task #rv75m9k, road B. JavaScript-changing and
value-identical. It runs after 99-method-value-properties (road A), whose tree its pins were taken on, and it never
lands alone: road A is its parent.

## Why

Road A turned the `@internal` methods tsc reads as values into readonly function-typed properties. What's left is 49
reads of public members (NodeFactory's creators, the hosts' members, the transformation result's hooks, the program's
getters) and of the five members the tree writes after building them, which road A leaves as methods. Each is still "a
method read as a value". A public member's declaration can't move, because typescript.d.ts would, so the change is at
the read.

## The edit

`adapt.cjs` and `mutant.cjs` are the receiver printer's engine (99-correctness-receiver-printer), byte for byte.
owners.json pins 21 whole owners in 10 files, the nearest named function holding each change, before and after with
SHA-256. Two of them sit inside another pinned owner and are checked but not written (`coveredBy`). The owners were
generated by a codemod over the tree, never by hand; the codemod and its generator are on the evidence branch.

Each of 43 reads takes one of three shapes:

- **A view, 28 of them over 38 reads.** Just before the read's statement:
  `const factoryView: { readonly createJSDocClassTag: (typeof factory)["createJSDocClassTag"] } = factory;`, and the
  read becomes `factoryView.createJSDocClassTag`. The view is the receiver's own object, so the read yields the same
  function object tsc reads today, unbound as tsc reads it: value-identical, and no call is added. It reads the receiver
  before the statement's earlier operands run, so every view's receiver is proven unwritable in between: its root is a
  const, or a parameter or variable the program never writes, and so is every link of its chain. Where a view serves an
  `if`'s presence test, the guarded block reads the member through the same view, calls included, so the narrowing
  holds and each call passes the same `this`.
- **An exact-parameter arrow, made once, for 5 reads.** Where a view can't serve: System's `directoryExists` and
  `createDirectory` (sys.ts's object holds them as literal methods, so a view of System stops at the read) become
  `systemDirectoryExists` and `systemCreateDirectory`, made once at the top of createCompilerHostWorker; and
  tsbuildPublic's `compilerHost.getCanonicalFileName`, whose receiver is `CompilerHost & ReadBuildProgramHost`, a value
  lowering can't hold as a view, becomes `compilerHostGetCanonicalFileName`, made once before each of its three
  statements, each run once per build state.

**Left, keeping their refusal, 6 reads:**

- the two save-then-override captures of `getSourceFile` on an intersection-typed host (watchPublic.ts and
  tsbuildPublic.ts): a view can't be held, and an arrow reads the member when called, after it's been overwritten, so
  it would call the override and recurse;
- `getCanonicalFileName` in tsbuildPublic's `toPath` and `relName`, per-call helpers where an arrow would be made on
  every call;
- `IdentifierNameMap.toKey`, twice: an arrow typed as `formatGeneratedName` expects moves its refusal to the generated
  name it hands toKey ("GeneratedIdentifier | GeneratedPrivateIdentifier seen as Identifier | PrivateIdentifier"), and a
  static field is read before its initializer. That's a relation question, not this family's.

## Premises a reader can re-check

- **A view is the receiver.** `const v = R` aliases the same object, so `v.m` reads what `R.m` reads, at the same
  moment in its statement's evaluation unless an earlier operand could rewrite R, which the never-written proof excludes.
- **A getter-backed member read through a view runs the getter.** NodeFactory implements its JSDoc creators as getters.
  finishAccessors rewrites every read of an accessor name into its dispatcher, so the view reads what tsc reads.
  internal/oracle's TestGetterReadThroughView pins it natively and on the JavaScript backend; a mutant that makes
  finishAccessors skip the read turns the native row red (Lower's ruling on #rv75m9k).
- **An arrow passes `this` = the receiver where tsc's unbound call passed undefined.** tsc already called these members
  with `this` undefined, so an implementation that read `this` would fail in tsc itself; none does (sys.ts and the hosts'
  members are arrows, function references and closures), and the whole lane is the witness (J-a8pyf3p).
- **An arrow reads its member when called, not when taken.** Adamic's two counts in `PROOF.md` hold it: no write to a
  wrapped member after the arrow is made, and no identity, `length` or `name` read where tsc's value flowed.
